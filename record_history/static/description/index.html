Record History

Keep a full snapshot of every change in a real history table — one typed column per tracked field, for any model

Odoo 18 Any Model Typed Columns Record Rules

Why another history module?

Odoo's chatter tracking (tracking=True) and generic audit logs store one line per changed field, as text. That is fine to read on a single record, but hard to answer questions such as "what was the total of every confirmed order last month, before it was edited?" Record History stores one row per version of the record, with real columns.

Chatter tracking Record History
Storage Old / new value per field, in messages Full snapshot per version, typed columns
Filter, group by, pivot, export ✗ ✓ like any other model
Requires mail.thread Yes No — works on any model
Kept after the record is deleted No Yes (optional)

How it works

Add history.mixin to the model to track, and create a small history model with history.line.mixin. The fields you declare on the history model are the fields that get tracked — no configuration screen, no field list to maintain.

from odoo.addons.record_history.models import source_selection class SaleOrder(models.Model): _inherit = ['sale.order', 'history.mixin'] _history_model = 'sale.order.history' class SaleOrderHistory(models.Model): _name = 'sale.order.history' _inherit = 'history.line.mixin' _description = 'Sale Order History' record_id = fields.Many2one('sale.order', ondelete='set null', index=True) # tracked fields: same name and type as on sale.order state = fields.Selection(selection=source_selection('sale.order', 'state')) partner_id = fields.Many2one('res.partner') amount_total = fields.Monetary() currency_id = fields.Many2one('res.currency')
  1. On create, a first snapshot is stored.
  2. On write, a new snapshot is stored only when a tracked value really changes, with the list of changed fields.
  3. On unlink, a last snapshot is kept when record_id uses ondelete='set null' (with ondelete='cascade' the history is deleted with the record).

Features

A real table per model

History rows have real columns: filter, group by user or date, build pivots and graphs, export to a spreadsheet.

Choose fields by declaring them

Char, number, date, selection, many2one, many2many… Any field declared on the history model with the same name and type as the source field is tracked.

"History" smart button

A smart button with the number of versions is added to the form views of tracked models automatically — no view to inherit.

Views generated for you

The history list and search views are built from the tracked fields, with the operation, the user, the date and the changed fields.

Follows your access rules

History lines inherit the record rules of their source record: users only see the history of records they are allowed to read.

Light on the database

Old and new values are read in batch, unchanged writes create nothing, and history_disable=True in the context skips tracking for imports and bulk updates.

Setup

  1. Add record_history to the depends of your module.
  2. Inherit history.mixin on the model to track and set _history_model.
  3. Create the history model with history.line.mixin, a record_id field and the fields to track.
  4. Add access rights for the history model — read-only for users is enough, history lines are written by the module itself.

Good to know

Record History tracks what goes through the ORM create / write / unlink of the tracked model:
  • Stored computed fields are compared when a write touches one of their direct dependencies. Changes coming from other records (e.g. editing an order line) do not create a snapshot on the parent.
  • One2many fields are not tracked — track the line model itself if you need its history.
  • Changes made with raw SQL bypass the ORM and are not recorded.
  • Use ondelete='cascade' or 'set null' on record_id; 'restrict' would prevent deleting records that have history.
