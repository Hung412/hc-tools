The history table

Every version of the record, as a row

Why Record History

One row per version, not one line per field

Chatter tracking is made to be read on one record. Record History is made to be queried across all of them.

Chatter tracking

✗  Old and new value of each field, as text in messages
✗  Cannot be grouped, pivoted or exported as data
✗  Only on models that inherit mail.thread
✗  Gone when the record is deleted

Record History

✓  A full snapshot per version, in typed columns
✓  List, pivot, graph and export like any model
✓  Any model, with or without chatter
✓  Can be kept after the record is deleted
For developers

Declare a field, it is tracked

Add history.mixin to the model to follow and write a small history model with history.line.mixin. Every field it declares with the same name and type as on the source model is tracked: no settings screen, no field list to keep in sync.

from odoo.addons.record_history.models import source_selection


class SaleOrder(models.Model):
    _inherit = ['sale.order', 'history.mixin']
    _history_model = 'sale.order.history'


class SaleOrderHistory(models.Model):
    _name = 'sale.order.history'
    _inherit = 'history.line.mixin'
    _description = 'Sale Order History'

    record_id = fields.Many2one('sale.order', ondelete='set null', index=True)
    # the tracked fields
    state = fields.Selection(selection=source_selection('sale.order', 'state'))
    partner_id = fields.Many2one('res.partner')
    amount_total = fields.Monetary()
    currency_id = fields.Many2one('res.currency')

On create

A first snapshot with every tracked field.

On write

A new snapshot only when a tracked value really changes, with the changed fields.

On delete

A last snapshot, kept when record_id uses ondelete='set null'.
What you get

Everything around the history, done for you

History smart button

Added to the form views of every tracked model, with the number of versions. No view to inherit.

List and search views generated

Built from the tracked fields, with date, user, operation, changed fields, filters and group-bys.

Follows your record rules

History lines inherit the rules of their source record: a user only sees the history of records they can read.

All the usual field types

Char, text, numbers, monetary, dates, selection, many2one and many2many, including stored computed fields.

Light on the database

Values are read in batch for the whole recordset, and a write that changes nothing tracked creates nothing.

Switch it off when needed

Pass history_disable=True in the context for imports and bulk updates.

How to use it

  1. Put record_history in your addons_path and add it to the depends of your module.
  2. Inherit history.mixin on the model to follow and set _history_model.
  3. Create the history model with history.line.mixin, a record_id field and the fields to track.
  4. Give it access rights: read-only for users is enough, history lines are written by the module itself.

Questions we get

Do I need the Discuss app or the chatter?
No. The module only depends on base and works on any model.

Are changes made by other records caught?
Stored computed fields are compared when a write touches one of their direct dependencies. A change coming from another record, such as editing an order line, does not create a snapshot on the order: track the line model itself if you need it.

Can I track one2many fields?
No, one2many fields are not tracked. Give the line model its own history instead.

What happens when a record is deleted?
With ondelete='set null' on record_id a last snapshot is kept with the record name; with 'cascade' the history is deleted with it. Avoid 'restrict': it would block the deletion.

Are changes made in SQL recorded?
No. Only what goes through the ORM create, write and unlink is recorded.
